## 1. 一句话结论

这个项目**不是“标准模式插件”或“创造模式插件”**，它是一个 profile（配置档）级插件包（bundle）。页面、HTTP API、状态机在两种模式下是同一套；真正随模式变化的是 **Agent 预设（preset）** 提供的工具面、能力和插件生命周期。

标准模式开发本身**不是 bug 的根因**。根因是项目把执行 Agent（worker）的预设、工具、只读边界都交给了“环境默认值 + 提示词（prompt）”，而没有显式的预设选择、沙箱（sandbox）模式和工具限制（tool restriction）。标准模式只是让这些假设正好成立，因此没有暴露问题；创造模式会放大它们。

## 3. 问题清单

### 3.1 P0：先修，否则治理链不成立

1. **执行 Agent 的预设是隐式的**
   - 位置：`packages/dsh-studio/src/host/dispatcher.ts` 的 `mount(agentCtx)`；`workshop-runner.ts` 同样。
   - 后果：默认预设是 `standard` 时一切正常；用户把创造模式设为默认后，worker 会拿到 `tool-cordis`、创作能力、plugin-manager（插件管理器），工具面和成本都变，但 Run 记录看不出来。
   - 修复方向：显式 `agentPreset`，默认固定为 `studio-worker`；`meta.agentPreset` + `mount(agentCtx, id)` 双写；记录实际绑定 id。

2. **“只读”角色没有硬约束**
   - 评审、研讨会、只做分析的派单都靠提示词说“不要改文件”，但 Agent 仍拿到 `write`、`edit`、`pwsh`，沙箱是 `workspace-write`。
   - 评审的 cwd 是 worktree：可在 Host 验证之后改代码并提交，旧验证/旧评审仍可放行。
   - 研讨会的 cwd 是主仓库：参与者可直接改主工作区。
   - 修复方向：`sandbox/mode: read-only` + `tools.restrict`（工具限制）+ 评审/研讨会专用最小预设；只读任务不要用主仓库作为 cwd。

3. **评审/验证/合并没有绑定到同一个提交**
   - `AgentRun` 没有 `commitSha`；`MergeProposal` 没有 `sourceCommit`。
   - `done` 只要求任意 review pass；合并提案只要求任意 verification pass；`merge.execute` 只检查分支存在。
   - 后果：验证或评审后分支被改写，仍可合并；合入的不是被验证的那一版。
   - 修复方向：Run 记录 `commitSha`/`baseSha`；提案记录 `sourceCommit`；`done` 与合并都要求“最新 Run 的提交”上的评审/验证；合并前校验分支头等于 `sourceCommit`。

4. **`/studio-api/boot` 对 `Origin: null`/`file://` 直接发令牌**
   - 位置：`packages/dsh-studio/src/host/router.ts` 的 `desktopOrigin` 分支；为真时跳过 `connection.admit()` 并返回进程令牌（token）。
   - 后果：本地 HTML、沙箱 iframe 等可能拿到令牌，进而调用所有 Owner（所有者）API。
   - 修复方向：至少移出 `file://` 与 `null`；更强方案是桌面端每次启动的随机 nonce（一次性随机数）或 DSH 认证 URL；令牌比较改为定时安全比较（constant-time）。

5. **项目包实际是全量状态包**
   - 导出：`exportState()` 全量；导入：`importState(state)` 替换全部。
   - 后果：分享项目 A 会带上所有项目的 prompt、决策、成本；在已有项目的机器上导入会覆盖其他项目（有 `pre-import` 备份，但不是“只导入这个项目”）。
   - 修复方向：导出按 projectId 过滤的项目切片；导入按项目合并，冲突时要求新 id 或拒绝；补多项目测试。

### 3.2 P1：高优先，随批次处理

- **外部执行器没有 Studio 侧沙箱**：Claude Code 以 `--permission-mode acceptEdits` 运行，Studio 只给 cwd；是否越界取决于 Claude Code 自身权限模型。Codex 有 `-s workspace-write`，相对更稳。
- **`approval/policy` 用裸 session（会话）事件写入**：应改用公开的 `approval.setPolicy(agent, "never")`；当前写法依赖 DSH 事件 schema。
- **插件卸载/HMR（热重载）留下孤儿 Run**：`apply` 只注销路由与 index injection（首页注入），没有跟踪活跃 AgentHandle；重载后任务可能永久停在 `running`。
- **硬依赖导致“降级”不成立**：`inject` 包含 `agents/agentPresets/agentDefaultModel/llm/tokenMeter`；缺一个 Cordis 不会调用 `apply`；`ctx.on` 缺失时直接 return，客户端 `/boot` 回退也没机会用。
- **预算语义不一致**：UI 写“单次任务 token 预算”，`beginRun` 按角色历史累计总额判断；子 Agent/workflow 的 token 不计入父 session 的 `tokenMeter.measure`。
- **blockers（阻塞项）不影响 Run 成功**：`completeRun` 只看 `summary` + `evidence`；有 blockers 的回执仍可 `succeeded` 并进入 `review`。
- **schema 降级会重建演示数据**：更高 schema 被当损坏；应保留文件并明确拒绝启动，而不是 seed。
- **profile 之间共享 `studio.json`**：`studio-test` 与 `desktop` 默认读写同一份 `~/.dsh/studio/studio.json`；e2e（端到端）隔离 profile 不等于隔离数据。
- **taskId 路径穿越**：`sanitize` 允许 `..`；导入状态只校验 `task.id` 是字符串；`.worktrees/..` 可能落到仓库根。
- **UI slot（插槽）key 过于通用**：`main` 用 `studio`、侧栏 id 用 `studio`；创造模式动态插件若用同名 key 会替换 Studio 入口。
- **Git 身份检查读全局配置**：`git config --get` 会读 global；应 `--local`。
- **测试缺口**：`dispatcher.ts`（687 行）、`router.ts`（1,487 行）没有单测；模式、boot 鉴权、bundle 多项目、commit 绑定、插件卸载都没有覆盖。

## 4. 修复原则

1. **先显式，再默认**：预设、沙箱、审批、工具白名单都写进 Run 记录；不允许“环境默认”决定 worker 能力。
2. **能下沉到系统，不写在提示词**：`sandbox/mode`、`tools.restrict`、`tools.guard`、`approval.setPolicy` 优先；提示词只做补充。
3. **fail closed（失败关闭）**：预设不存在、沙箱不可用、分支头不符、验证不是最新提交时，拒绝派单/合并，不要回退到默认。
4. **不改变用户已有数据语义**：schema 变更必须有迁移；更高 schema 不得 seed；项目包导入不得覆盖其他项目。
5. **批次交付**：按 AGENTS.md，一次批次完成同类改动，最多两次全量验证（一次红灯定位、一次绿灯收尾）。

## 6. 批次 A 详细建议

### 6.1 `/boot` 鉴权

- 移除 `file://` 和 `origin === "null"` 的信任；只保留 `dsh-app://` 也不够，因为原始 HTTP 客户端可以伪造 `Origin`。
- 更强方案：
  - 桌面端启动时由 shell 生成一次性 nonce，通过 index injection 注入页面；`/boot` 要求 `x-dsh-studio-desktop` 请求头匹配 nonce；nonce 只存进程内存。
  - 或者让桌面端走 DSH 认证 URL/连接，不再绕过 `connection.admit()`。
- 所有分支都做速率限制和定时安全比较；令牌不写日志。
- 测试：`Origin: null` → 401；无 nonce 的 `dsh-app://` → 401；正确 nonce → 200；普通同源页面 → `connection.admit` 通过才 200。

### 6.2 提交绑定

- `AgentRun` 增加：`commitSha: string | null`、`baseSha: string | null`。
- `MergeProposal` 增加：`sourceCommit: string | null`、`baseCommit: string | null`、`reviewId: string | null`、`verificationRunId: string | null`。
- `WorkspaceManager.prepare` 返回 base commit；`commit` 返回 commit SHA（当前已有返回值，但 dispatcher 没记录）。
- `completeRun` 记录 `commitSha`/`baseSha`；`createMergeProposal` 要求：
  - 最新代码 Run 的 `verification` 通过，且 `verification.runId === latestRun.id`；
  - 最新代码 Run 的 `review` 通过，且 `review.runId === latestRun.id`；
  - `git rev-parse <branch>` 等于 `latestRun.commitSha`。
- `transitionTask` 的 done 门禁同样要求“最新代码 Run 的评审通过”，不是任意一次。
- `merge.execute` 合并前再次校验分支头；不匹配就拒绝，并提示重新验证/评审。
- 迁移：schema 26 → 27，给旧 Run/Proposal 补 `null`，旧数据不伪造 SHA。

### 6.3 项目包

- 导出：构造 `ProjectSlice`（项目切片），只包含选定项目及其 roles/tasks/branches/runs/reviews/verifications/decisions/stageGates/triggers/threads/workshops/demos/providerProfiles/modules/contractChanges。
- manifest 记录 `projectId`、切片包含的 id 列表、文件 SHA-256。
- 导入：校验切片、按项目 id 合并；同 id 冲突时要求新 id 或拒绝；不要 `importState` 全量替换。
- 解压前先 `tar -tzf` 列出条目，拒绝绝对路径、`..`、盘符路径；再解压到临时目录。
- 测试：项目 A + 项目 B 同时存在，导出 A 不包含 B；导入 A 不删除 B；恶意 tar 被拒。

### 6.4 路径与 worktree（任务工作树）

- `sanitize(taskId)` 增加：拒绝 `.`、`..`、空、保留名；目录名用 `sanitize + '-' + sha256(taskId).slice(0, 8)`。
- `path.resolve(worktreeRoot, key)` 后再校验前缀，防止 `..`。
- `prepare` 遇到已存在目录时，用 `git worktree list --porcelain` 校验目录与分支；不匹配就报错，不要直接复用。
- 测试：`taskId=".."` 拒绝；已存在但分支不符拒绝。

### 6.5 schema 降级与数据目录

- `load()`：`schemaVersion > STUDIO_SCHEMA_VERSION` 时**不要** seed；保留文件、设置 warning、让页面显示“版本过新，请升级插件/恢复备份”。
- 损坏 JSON 仍可备份 + seed，但要区分“损坏”和“版本过新”。
- 数据目录：支持 `DSH_STUDIO_DATA_DIR` 环境变量；测试和 e2e 必须指向临时目录。是否按 profile 分目录是产品决策，不要静默改默认路径。

### 6.6 Git 身份

- `git config --local --get user.name` / `user.email`；缺失时明确报 `git_identity_required`，不读全局。

## 7. 批次 B 详细建议

### 7.1 新预设

在 `packages/dsh-studio/cordis.patch.yml` 增加一个 `studio-worker` 预设（`@deepseek-ai/dsh-agent-preset` 行），最小工具集：

- 保留：`persona`、`agent-instructions`、`time-context`、`tool-pwsh`/`tool-bash`、`tool-fs`、`tool-fs-search`、`tool-jobs`、`tool-web`、`tool-skill`、`present`。
- 移除：`tool-subagent`、`tool-subagent-fork`、`workflow`、`tool-ask-user`、`tool-schedule`、`tool-goal`、`tool-todo`、`tool-cordis`、`tool-plugin-manager`、`tool-plugin-market`、`tool-working-directory`。
- 评审用 `studio-review`：只读工具 + `sandbox/mode: read-only`；不要 `write/edit`，不要 `subagent/workflow`，不要插件工具。
- 如果不想在插件包里声明预设，退而求其次：显式 `mount(agentCtx, "standard")` + `tools.restrict` 去掉全局工具；但标准预设仍含 subagent/workflow/ask/plan，隔离不如专用预设。

### 7.2 派单代码

- `Role` 或 `Project` 增加 `agentPreset`（默认 `studio-worker`）；UI 设置页展示，不允许普通用户随意选 `creator`。
- `dispatcher.execute`：
  - `meta: { cwd, agentPreset: presetId }`；
  - `const bound = await ctx.agentPresets.mount(agentCtx, presetId)`；
  - `if (bound.id !== presetId) throw ...`（fail closed）；
  - `ctx.approval.setPolicy(agent, "never")`（需要 inject `approval` 或用 `ctx.get`）；
  - `ctx.tools.restrict({ deny: [...] })` 去掉 profile 全局工具；
  - 记录 `agentPreset`/`approvalPolicy`/`sandboxMode`/`toolNames` 到 Run。
- 评审/研讨会/只做分析的派单：`sandbox/mode: read-only`；cwd 用临时目录或只读 worktree；`tools.restrict` 去掉写工具。
- 不要用 `process.cwd()` 给只读 Agent 当 cwd；那是 Host 的启动目录。

### 7.3 审计

- Run 详情显示：实际预设、审批策略、沙箱模式、工具数量/哈希。
- 如果实际预设与配置不一致，页面警告；不要静默。

## 8. 批次 C 详细建议

- `AgentDispatcher` 维护 `activeHandles: Set`；`apply` 的 `ctx.effect` 返回 disposer 时调用 `dispatcher.shutdown()`：abort/dispose 所有 handle，并把对应 Run 标记 failed（失败）。
- 启动时 `reconcileRuns()`：把 `queued/running` 且没有活跃 handle 的 Run 标记 failed，任务回到 `ready` 或 `blocked`，写事件；不要静默。
- `completeRun`：`receipt.blockers` 非空时，Run 记 `failed`（或至少不进 `review`），任务回 `ready`/`blocked`；补测试。
- `transitionTask`：`blocked -> ready` 若已有 2 次失败且没有重拆（resplit）票/显式豁免，拒绝；避免第三次原地重试。
- `ctx.on` 可选：先注册 `/studio-api` 路由；`webserver/index-inject` 不存在时只跳过注入，客户端仍可 `/boot`。
- `inject` 拆分：核心 `webServer/connection` 必须；`agents/agentPresets/agentDefaultModel/llm/tokenMeter` 用 `ctx.get` 可选；缺 dispatch 能力时页面可用，派单接口返回 503 和明确错误。
- 客户端 401：`resolveStudioBoot()` 重新取 `/boot` 并更新 token；插件重载后页面不必手动刷新。
- slot key 改为 `dsh-ai-studio`（`main` 和侧栏 id 一致），降低冲突。

## 9. 测试计划

### 新增单测（建议 15–20 个）

- `router`：`/boot` 无鉴权/`Origin: null`/无 nonce → 401；正确 nonce → 200；数据接口无 token → 401。

- 插件重装/重载后页面仍可用（401 自动恢复）。

## 13. 会话模式问答（标准模式 vs 创造模式）

### 13.1 标准模式开发是不是问题？

不是。这个项目是 profile 级插件包，用标准模式的文件/终端工具开发是合适的；创造模式的动态插件工具反而不适合作为它的运行时依赖。

但“只在标准模式验证”掩盖了模式耦合：

- 默认预设是 `standard`，`mount()` 不传 id 正好工作，所以没有测试“默认是 creator”的情况；
- 标准会话没有 `tool-cordis`，但 profile 里的其他插件仍可能注入 `plugin_manager`/`cordis_inspect`，所以工具面不是纯净的；
- 标准开发流程是“改文件 → build → install → restart”，不会覆盖创造模式的 live 插件安装/HMR/令牌轮换；
- 没有测试动态 client 插件与 Studio 的 slot key 冲突、Owner 令牌信任边界；
- 评审/研讨会可写、合并可漂移这些问题在标准模式下也存在，只是创造模式会放大。

### 13.2 在哪里修？

建议在**项目开发会话**，或在 `D:\dsh-ai-studio` 新建一个实现会话。原因：

- 项目的 `AGENTS.md` 交付节奏、计划表、批次、版本/文档/安装/提交/发布都在那个上下文里；
- 分析会话的上下文已经很长，继续做实现容易混入分析结论、增加 token 成本；
- 修复需要红灯/绿灯、迁移、E2E，独立实现会话更干净。

如果开发会话已经很长/被污染，**新建会话**也可以；把本文档作为交接，先读 `AGENTS.md`、`CONTEXT.md`、`docs/00-设计蓝图.md`。

### 13.3 能否命令 AI 把开发会话改成创造模式？

**不能通过对话让 AI 直接改当前会话的预设。** 原因：

- DSH 的 Agent 预设是在会话第一轮之前确定的；会话开始后，`agentPreset` 是持久事实，不能原地切换；
- `agentPresets.select()` 只针对空白 Agent（还没开始第一轮）；`recompose()` 也只针对空白 Agent；
- AI 没有“切换自己 UI 会话预设”的工具；它不能替用户点模式选择器。

用户操作：

- 新建会话时，在模式选择器里选「创造模式」；
- 或在一个空白会话里切换；
- **不要**为了省事把创造模式设为新任务默认；这会让 Studio 的 worker 默认拿到 creator 工具（如果还没修批次 B）。

如果只是想在创造模式里做修复：新建一个创造模式会话，粘贴第 0 节的启动指令即可。但修复本身**不需要**创造模式；标准模式更接近最终用户环境，也更适合验证 profile 插件。

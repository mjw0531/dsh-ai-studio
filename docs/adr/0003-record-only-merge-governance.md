# 合并治理只记录状态，不自动执行 Git

## 背景

v0.2 需要让「支线汇入主干」可审计：提案、风险、回滚、评审、批准、合并记录。最直接的做法是让 Host 在项目仓库里执行 `git merge`，但 Studio 会被安装到任意仓库，自动合并可能遇到脏工作区、错误分支、未提交改动、资产冲突，且不可逆。v0.1 也还没有 Project→repoPath 的绑定和 Git worktree 隔离。

## 决策

v0.2 把**验收**和**合并**分开：

- 任务必须先 `done`（验收通过、证据齐全），才能提交合并提案。
- 合并提案有 `review → approved → merged` 和 `review → rejected` 四态。
- Studio 记录摘要、风险、回滚、评审备注、合并提交 SHA，并展示人工执行命令：
  `git switch <base> && git merge --no-ff <branch>`。
- Studio 不执行 Git 命令，不读取/修改用户仓库。
- 打回提案时，任务退回 `running`，需要重新验收后再提交。
- 一个任务最多有一个活跃提案（review/approved/merged）；rejected 后可以重新提交。

## 考虑过的选项

1. **自动执行 `git merge`**：体验最顺，但风险最高；需要干净的 repo、明确的 base、冲突处理和回滚策略，v0.2 还不具备。
2. **只做 proposal 记录**（选中）：安全、可在任意项目使用，先把治理闭环跑通；Git 执行留给后续有明确 repo 绑定和审批的版本。
3. **直接做 worktree + 合并队列**：更接近最终形态，但会把 v0.2 拖成一个大版本，且还没有 Agent 执行层来消费 worktree。

## 后果

- 合并仍需要人/Integrator 手动执行；Studio 的「已合并」是记录，不是 Git 事实。UI 必须明确这一点，避免误以为已经合并。
- `mergeCommit` 允许人工回填 SHA，为后续自动校验留字段。
- 未来接入 Git 时，应新增显式的 `repoPath`、干净工作区检查、冲突处理和审批门禁，而不是直接在这个记录接口里偷偷执行。
- 打回会重开已验收任务，这是有意的：合并失败/评审不通过意味着工作还需要改。

# dsh-ai-studio 使用说明书

适用于 **v3.13.1 / DSH 0.2.1-rc.2**。

## 1. 它是什么

dsh-ai-studio 是 DeepSeek Harness 的插件。它把一个 DSH 会话扩展成一间 AI 工作室：

- 有项目、角色、任务、验收、证据；
- 有 Agent 派单、独立验证、独立评审；
- 有决策台、ADR、合并提案和合并后回归；
- 所有治理记录保存在本地 `studio.json`，代码和文档保存在项目仓库。

它不是另一个聊天窗口，也不替代 DSH。

## 2. 安装与打开

1. DSH → **Plugins → Add plugin**，选择 `dsh-ai-studio-3.13.1.tgz`。
2. 完全退出 DSH（含托盘），重新打开。
3. 左侧点击 **AI 工作室**。
4. 首次打开会自动创建：
   - 一个「示例项目」；
   - 4 个角色：Lead、Architect、Builder、Verifier；
   - 5 个示例任务。
5. 右上角可以改「工作室名称」，默认 **AI工作室**。
6. 切到 DSH 对话再回到「AI 工作室」，会保留上次的页签和打开的任务；不需要重新点到初始页。

## 3. 核心对象

| 中文 | 英文 | 说明 |
|---|---|---|
| 项目 | Project | 一个仓库 + 文档 + 角色 + 任务 |
| 角色 | Role | 职责契约，不是聊天人格 |
| 任务 | Task | 一条可验收的工作 |
| 验收项 | Acceptance | 全部完成才能 done |
| 证据 | Evidence | 测试输出、命令、评审、验证 |
| 运行 | Run | 一次 Agent 执行记录 |
| 评审 | Review | 独立只读评审 |
| 验证 | Verification | Host 执行的命令和退出码 |
| 决策 | Decision | 项目级拍板记录 |
| 合并提案 | Merge Proposal | review → approved → merged |

## 4. 第一次配置

### 4.1 绑定项目仓库

设置 → 代码仓库 → 绑定 / 更换仓库，填写项目仓库绝对路径。

绑定后：

- 每个任务自动创建 `.worktrees/<taskId>`；
- 分支名 `studio/<taskId>`；
- Agent 只改 worktree，不碰主工作区。

### 4.2 配置角色

角色页可以配置：

- 使命、职责、非目标、决策权；
- 模型（DSH 已配置的模型路由）；
- 单任务 token 预算、每日 token 预算。

角色页的「执行器」支持：

- **DSH Agent**：走 DSH 的模型路由，支持 DeepSeek 等已配置 Provider；
- **Claude Code**：本机 `claude` CLI，要求先登录；
- **Codex CLI**：本机 `codex` CLI，要求先登录。

Claude Code / Codex 在任务 worktree 内以 headless 模式运行，Host 仍然：

1. 自动提交改动；
2. 让回执走 `summary + evidence` 门禁；
3. 执行契约越界检查；
4. 不把外部工具的输出当成验收结论。

Cursor 目前只有 IDE 启动器，没有 headless Agent，所以暂不支持。

直接填写 GPT/Claude/GLM/Kimi API Key 的 ProviderProfile UI 还未做；当前外部模型要么在 DSH 里配置 Provider，要么用 Claude Code/Codex 的登录态。

### 4.3 项目知识

知识页可以绑定：

- PRD；
- INVARIANTS；
- MODULES。

绑定后，任务 done 前必须勾选「文档已同步」。

### 4.4 阶段门禁（v2.6）

新项目从「需求探索」开始，项目页顶部显示四个阶段：

```text
需求探索 → 架构设计 → 原型验证 → 持续开发
```

进入下一阶段前，Owner 要：

1. 点「准备阶段门禁」；
2. 完成检查项；
3. 至少登记一个产物（如 `docs/PRD.md`）；
4. 写门禁说明；
5. 点「批准进入」。

如果确实要跳过未完成项，必须填写 **Owner 豁免理由**，会记录在门禁里。  
拒绝门禁必须写理由。

约束：

- 绑定代码仓库的项目，只有进入「持续开发」后才能派单；
- 无仓库的分析任务不受此限制；
- 已批准的门禁不能再改；
- 旧项目自动迁移为「持续开发」，不会打断现有工作；
- 从原型验证进入持续开发前，必须登记一个 `demo` 产物（Demo 路径、URL 或 playtest 记录），或写 Owner 豁免理由。

### 4.5 触发收件箱（v2.7）

项目页的「触发收件箱 / Trigger Inbox」接收外部事件：

- 手动捕获；
- GitHub / CI / IM / 邮件来源（当前通过 API 或手动捕获，Webhook 适配器后续接入）；
- 同一 `threadKey` 归入同一条 Thread；
- 后续同 Thread 事件可以关联到已有任务。

处理方式：

1. 填事件标题、正文、Thread key；
2. 点「捕获」；
3. 在待处理列表里点「转为任务」，或点「忽略」并写理由；
4. 转为任务后，任务默认带一条验收标准，可继续编辑；
5. 不会自动派单、不会自动 merge。

### 4.6 研讨会（v2.8.1）

项目页的「研讨会 / Workshop」用于记录多角色独立意见：

1. 填标题、议题，选择阶段和参与角色；
2. 点「AI 独立评审」，每个参与角色独立调用 DSH Agent；也可以手动粘贴意见；
3. 写汇总；
4. Owner 写最终决策；
5. 记录结论，不自动合并。

原则：

- 独立提交，不在同一个上下文里轮转；
- 保留反对意见和风险，不追求 AI 一致；
- 汇总和决策由人确认；
- AI 评审失败会记录为缺失意见，不能视为同意。

### 4.7 Provider Profiles（v2.10）

团队页的「Provider Profiles」用于保存命名执行配置：

- 名称；
- 执行器：DSH Agent / Claude Code / Codex；
- DSH provider（可空）；
- 模型 ID（可空）。

角色绑定 Profile 后，派单、独立评审和 Workshop 会优先使用 Profile 的配置；不绑定则使用角色自己的执行器/模型。

约束：

- Profile 属于当前项目；
- 被角色使用的 Profile 不能删除；
- Claude Code / Codex 仍然只能用于已绑定代码仓库的任务；
- 空 provider/model 表示继承默认。

### 4.8 Provider 健康度（v2.12）

团队页的 Provider Profile 行会显示：

- 健康状态：`unknown` / `healthy` / `degraded`；
- 成功次数 / 总运行次数；
- 失败率；
- 累计 token；
- 最近一次失败错误。

诊断数据：

- 失败原因分布：回执、超时、Provider/模型、任务、未知；
- 最近 5 次运行；
- 对 `degraded` Profile 给出备用 Profile 建议。

聚合规则：

- 只看绑定该 Profile 的角色产生的 Run；
- 没有 Run 时为 `unknown`；
- 最近一次 Run 失败时为 `degraded`；
- 历史失败但最近成功时为 `healthy`，失败次数仍保留。

健康度只是观察，不会自动切换 Profile；切换仍由 Owner 决定。

### 4.9 人工备用切换（v2.13）

当 Profile 为 `degraded` 且存在建议 Profile 时：

1. 点建议旁的「改绑」；
2. 确认要把所有绑定当前 Profile 的角色改绑；
3. Studio 更新角色绑定，并写入 `provider.reassigned` 审计事件。

约束：

- 不自动切换，必须由人确认；
- 只改绑定，不修改任务/分支；
- 建议 Profile 必须属于同一项目；
- 没有角色绑定时不能改绑。

### 4.10 Run 执行快照（v2.14）

每次派单创建 Run 时，会记录：

- `providerProfileId`；
- `executor`；
- `provider`；
- `model`。

健康度优先按 Run 快照聚合；只有旧 Run 没有快照时，才回退到当前角色绑定。

因此改绑 Profile 后：

- 新 Run 归属新 Profile；
- 旧 Run 仍归属当时使用的 Profile；
- 不会再出现“改绑导致历史失败率整体搬家”。

### 4.11 Provider 实时探测（v2.15）

Provider Profile 行新增「探测」按钮：

- DSH Profile：检查 provider 是否存在、模型是否在模型列表；
- Claude Code / Codex：检查本机 CLI 是否可执行；
- 结果显示「探测通过 / 探测失败」和原因；
- 结果不持久化，刷新后消失；
- 不自动切换 Profile，也不修改任务。

外部 CLI 探测只验证命令存在，不验证登录状态；实际任务仍以运行结果为准。

### 4.12 Trigger Webhook（v2.16）

端点：

```text
POST /studio-api/webhooks/:projectId/github
POST /studio-api/webhooks/:projectId/ci
POST /studio-api/webhooks/:projectId/im
```

服务端必须设置：

```text
DSH_STUDIO_WEBHOOK_SECRET
```

请求头：

```text
X-Hub-Signature-256: sha256=<HMAC-SHA256(body)>
```

或：

```text
X-Studio-Signature: sha256=<HMAC-SHA256(body)>
```

处理流程：

1. 校验 HMAC；
2. 检查项目 Webhook 是否启用；
3. 检查 source 是否允许；
4. 按 repo / label / author / mention 做确定性过滤；
5. 命中后写入 Trigger Inbox；
6. 人工确认后才转 Task；
7. 不自动派单、不自动 merge。

未命中会记录 `trigger.webhook_filtered` 事件，不创建 Trigger。

当前没有 LLM 语义过滤；只有确定性规则。

### 4.13 Prototype 手动 Demo 记录（v2.17）

项目处于「原型验证」阶段时，项目页会出现「原型 Demo 记录」：

- 标题；
- 入口 URL / 路径；
- 启动命令（只记录，不执行）；
- 验证步骤；
- 结果：通过 / 失败；
- 截图 / 录像路径；
- 已知限制；
- 记录人。

规则：

- 通过（`passed`）的 Demo 记录可以作为进入持续开发的 demo 证据；
- 失败记录不会满足门禁；
- 可以手动切换结果；
- Studio 不启动进程、不检测端口、不自动截图；
- 不自动 merge。

### 4.14 Workshop AI 汇总草稿（v2.18）

研讨会已有至少一条参与者意见后，可以点「AI 汇总草稿」：

- 生成共识；
- 生成分歧；
- 生成未决问题；
- 生成候选方案。

边界：

- 草稿单独保存为 `aiSummary`；
- 不覆盖原始 `notes`；
- 不自动写入 Owner synthesis；
- 不自动写 decision；
- 不自动 merge；
- 汇总失败不影响原始意见。

Owner 需要自己确认汇总，再决定是否采纳。

### 4.15 入门引导与项目模板（v2.19）

公司页会出现「开始使用」清单：

1. 创建项目；
2. 创建角色；
3. 创建第一个任务；
4. 绑定代码仓库。

步骤完成或手动关闭后不再显示。

新建项目时可以选择模板：

- Web 应用；
- 游戏原型；
- CLI 工具。

模板会自动创建对应的角色和首批任务，之后仍可自由修改。

> 独立窗口 / PWA 暂缓：它需要 DSH 提供稳定的入口和资源路由；当前继续使用 DSH 页面，避免依赖私有路由。

### 4.16 公司级组合治理（v3.0）

公司页新增「公司级组合」：

- 组合预算：已用 / 总预算、超预算项目数、未配置项目数；
- 跨项目优先级：未完成任务按 P0/P1/P2 和老化时间排序；
- 角色覆盖：同名角色跨项目数、活跃任务数。

约束：

- 全部从项目状态派生，不保存第二份事实；
- 点击优先级只打开对应项目；
- 不自动派单、不自动调整预算；
- 跨项目角色只做聚合展示，角色本身仍属于项目。

## 5. 日常流程

### 5.1 建任务

任务页 → 新建任务：

- 标题、目标、优先级；
- 负责人、验收人（建议不同角色）；
- 验收标准，一行一条；
- 验证命令，例如 `npm test`；
- 模块、契约引用；
- 需求引用（PRD 条目或需求 ID，用于追溯）；
- 票类型：
  - 新建型：red→green；
  - 改修型：必须先写「诊断」和「修改计划」。

### 5.2 派单

任务详情 → 派单。

Host 会：

1. 创建 worktree 和分支；
2. 用角色配置调用 DSH Agent；
3. 等 Agent 输出结构化回执；
4. 把 Agent 改动自动 `git add` + commit 到任务分支；
5. 任务进入 `review`。

回执必须包含 `summary` 和至少一条 `evidence`，否则 Run 失败。

### 5.3 Host 验证

任务详情 → 验证。

Host 在 worktree 里执行任务上保存的验证命令，记录：

- 命令；
- 退出码；
- 输出；
- 通过/失败。

在页面上改命令会先更新任务的 `verifyCommand`，再执行；`/studio-api/tasks/:id/verify` 不再接受请求体里的临时命令，避免 token 泄露后直接执行任意命令。

通过只写 evidence，不会自动勾验收，也不会自动 done。

### 5.4 独立评审

任务详情 → 独立评审。

验收人角色会新开一个只读 Agent 会话，检查：

- diff；
- Host 验证输出；
- 验收标准；
- 契约边界。

返回 pass/fail + findings。代码任务没有 pass 不能 done。

### 5.4.1 执行预设与只读边界

Studio 不让“当前会话模式”决定 worker 的工具面：

- worker、评审、Workshop 都显式挂载 `standard`；
- worker 禁止子代理、workflow、计划/目标/定时、插件管理器和 Cordis 创作工具；
- 评审和 Workshop 再禁止 `write/edit/pwsh/bash`，并使用 `read-only` 沙箱；
- 每次 Run 记录实际预设、审批策略、沙箱模式和被限制的工具；
- 如果 DSH 没有 `tools.restrict` 能力，派单直接失败，不会退化成无限制运行。

因此：在创造模式里派单，worker 仍然是 `standard`，不会拿到 `creator` 的 Cordis/插件工具。

### 5.5 完成

人勾完所有验收项，补至少一条 evidence；如果项目有知识文档，勾「文档已同步」；然后：

`review → done`

### 5.6 合并

done 后创建合并提案：

- 摘要；
- 回滚方式；
- 风险；
- 分支、base。

流程：

`review → approved → merged`

执行真实 `git merge --no-ff` 前，Host 检查：

- 提案 approved；
- 当前在 base；
- 工作区干净；
- 分支存在；
- repo 配了 `user.name/email`。

冲突自动 abort，不自动 push。

### 5.7 合并后回归

merge 成功后，Host 在项目仓库执行任务验证命令。

- 通过：记录 post-merge Verification；
- 失败：自动生成一条「合并后回归失败」决策，附 merge commit 和回滚建议；不会自动回滚。

### 5.8 人工回滚

只有 merged 且 post-merge 回归失败的提案可以回滚：

`git revert -m 1 --no-edit <mergeCommit>`

记录 rollback commit；不 reset、不 push。

## 6. 决策台

「决策台」（Decision Desk）处理：

- Agent 提出的项目级决策；
- 人手动提出的决策；
- 跨支线契约冲突；
- 连续失败升级；
- 合并后回归失败。

Owner 可以批准/拒绝，必须留结论和理由。

`reversible=false` 的决策批准时，自动生成 Markdown ADR 草稿；人工确认后可以「写入 docs/adr」。

## 7. 失败与门禁

- 连续失败 2 次：任务 blocked，生成决策，并自动生成 Architect 重拆 ticket；
- 契约越界：blocked + 决策；
- 每完成 3 个任务：自动生成一张集成/playtest ticket（不自动派单）；
- 合并前没有 Host 验证 pass：不能提交提案；
- 代码任务没有独立评审 pass：不能 done。

## 8. 数据、备份与迁移

### 8.1 数据在哪

- 治理状态：`%USERPROFILE%\.dsh\studio\studio.json`
- 代码：项目仓库
- 文档：项目仓库
- 任务分支：项目仓库 `studio/<taskId>`
- worktree：项目仓库 `.worktrees/<taskId>`（本机临时目录）

### 8.2 备份

页面右上角「导出」下载完整 JSON；「导入」恢复。

导入时 Host 会：

1. 备份当前文件为 `studio.json.pre-import-*`；
2. 校验 schema 和结构；
3. 拒绝更高 schema；
4. 成功后才替换。

### 8.3 换设备

1. 新机安装 DSH + 插件；
2. 导入 `studio.json`；
3. clone 项目仓库；
4. 在设置里重新绑定 `repoPath`；
5. 旧 worktree 不迁移，任务分支从 Git 仓库恢复。

### 8.4 项目包（Project Bundle）

设置 → 代码仓库 → **导出项目包**，生成 `tar.gz`，包含：

- `project.json`：单个项目的 `ProjectSlice`（项目、角色、任务、Run、评审、验证、决策等）；
- `project.bundle`：`git bundle --all`，含所有分支；
- `manifest.json`：项目、schema、插件/DSH 版本、生成时间、格式版本 2；
- `README.txt`：迁移步骤。

设置页也可以「导入项目包」：输入项目包绝对路径和目标仓库目录（必须为空或不存在），Host 会：

1. 校验 tar 路径、manifest 和 SHA-256；
2. 解压项目包；
3. `git clone project.bundle <target>`；
4. 只合并 `project.json` 里的项目，不替换其他项目；
5. 同 project id 拒绝；重新绑定 `repoPath`。

v1 项目包（整份 `studio.json`）会被拒绝，避免导入一个项目覆盖整台机器。

受保护的源仓库不会被覆盖；目标目录非空时明确拒绝。恢复后，活跃任务第一次派单会从 `origin/studio/<taskId>` 重建 worktree。

项目包不含 API Key；Claude Code/Codex 需要在新机重新登录。

## 9. 当前限制

- DSH Agent 只使用 DSH 已配置的模型路由；
- 没有 Studio 侧 GPT/Claude/GLM/Kimi API Key 配置 UI；
- Claude Code / Codex 执行器已接入，但需要本机先登录；
- 没有 Cursor 执行器（Cursor CLI 不是 headless Agent）；
- 项目包导入需要手动输入本地绝对路径；
- 没有独立 OS 窗口/PWA；
- 没有自动回滚；
- 没有跨厂商强制评审；
- 只在 DSH `0.2.1-rc.2` 上验证。

## 10. 故障排查

| 现象 | 处理 |
|---|---|
| 页面提示 Host 旧版本 | 完全退出 DSH 后重启 |
| Agent 能改文件但不能跑测试 | Windows ACL 限制；用 Host 验证 |
| 合并报 `Committer identity unknown` | 给 repo 配 `user.name/email` |
| 导入报 schema 不支持 | 导入文件比当前插件新，先升级插件 |
| 导出文件很大 | 包含 prompt/输出/评审记录，属于正常 |
| 找不到侧栏 | 确认插件已安装并重启 DSH |

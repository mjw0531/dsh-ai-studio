# 工作流评审：DSH 会话 + Kimi 对话 vs Studio

## 来源

- DSH 会话 `session-3f8002a3-c303-4961-b2de-fabf339602cc`（Unity/Claude Code 安装讨论，后半段是游戏开发工作流）。
- Kimi 分享：[AI助力MOBA开发](https://www.kimi.com/share/1a15f6ef-8c22-8df2-8000-00000ca42334)。
- 两个来源的结论高度一致：**范围控制 > 模型选择；上下文喂窄 > 任务写短；独立验收是 AI 开发唯一的刹车。**

## 两段对话里的工作流

### A. DSH 会话的版本

1. **文档是第一要点**：PRD 单一事实源，所有改动同步文档；ADR/模块文档/CONTEXT 防止前后矛盾。
2. **模块拆分**：边界清楚，AI 分析问题时能直接对应到具体模块。
3. **短任务**：每个任务阶段化，完成一段回看任务表再继续。
4. **验收升为第四要点**：验收先于实现；测试不能由实现者自己写，必须独立会话/独立角色。
5. **上下文喂窄**：实现者会话只喂「模块接口卡 + 一个 ticket」，不喂整份 PRD。
6. **按角色分配模型**：PRD 拷问者、架构师、实现者、调试者、验收者、整合者；同一模块不同阶段也要换模型。
7. **5 分钟技术纵切片**：在架构和全面实现之间插一道闸，先解决横切问题（asmdef、输入、相机、逻辑帧、测试框架、构建）。
8. **不可逆决策**：网络预留、确定性、逻辑/表现分离，必须在 PRD 阶段拍板。

### B. Kimi 的版本

Kimi 在原三要点上补了更完整的执行层：

- **第零要点：范围控制**：3~5 英雄、1 张地图、单机 bot + 轻剧情；MOBA 是最重的独立游戏品类之一。
- **文档分层**：`PRD.md` / `GDD/` / `ARCHITECTURE.md` / `modules/*.md` / `ADR/` / `CONVENTIONS.md` / `TASKS.md`。
- **模块契约卡**：每个模块一页，写职责、接口、依赖、禁区；实现者开场只喂契约卡 + ticket。
- **Ticket 载荷**：目标 / 涉及模块 / 接口约束 / 验收标准 / 禁止事项。
- **独立验收 AI**：必须自己跑命令，不接受实现者转述的测试输出；表现层还要人玩。
- **交叉验收**：实现与验收用不同模型家族，避免同家族盲点。
- **两条回路**：契约错了回架构师；同一 ticket 失败 2 次退回重拆。
- **集成验收**：每 5~8 个 ticket 或每周插一个「可玩 build + 人玩 10 分钟」。
- **人的两个 gate**：契约/ticket 批准、关单确认；其余自动化。

## 优点

- 把「AI 开发」从聊天提升为**可审计流水线**：意图 → 契约 → ticket → 实现 → 独立验收 → 关单。
- 承认**上下文是主要矛盾**：不是把任务写短，而是把上下文喂窄。
- 把验收从“测试环节”提升为**任务定义的一部分**，且要求独立于实现者。
- 有回路：契约升级、重试上限、集成验收，避免直线流程的文档漂移和无限重试。
- 强调**范围控制**和**不可逆决策**，对个人开发者尤其重要。

## 缺点 / 风险

- **依赖人写 PRD**：个人开发者最容易跳过；没有 PRD 的“文档驱动”会退化为注释驱动。
- **模块契约卡仍是人工维护**：没有工具强制“实现者不许改契约”，容易在代码里就地打补丁。
- **独立验收 AI 没有环境就无法真跑**：Unity batchmode、依赖、许可证都是门槛；没有执行的验收会退化成读代码。
- **模型分工过细**会交“上下文税”；一主一备 + 专项工具通常更现实。
- **没有代码级隔离**：文档流程再好，多个 AI 在同一工作区写仍会互相污染（这需要 worktree）。
- **没有成本/预算闭环**：token 是边际成本，流程没有预算门禁。
- **集成验收/人工手感**难以自动化，需要明确“人类是唯一验收设备”的场景。

## 对比当前 Studio

| 工作流要素 | 当前 Studio | 差距 |
|---|---|---|
| PRD 单一事实源 | 只有项目 description；无 PRD/Project Book | ❌ 缺 |
| 模块拆分/契约卡 | Task 有 goal/acceptance，无 module/contract | ❌ 缺 |
| 文档同步/ADR | 有 Studio 自身 ADR，项目级 ADR 未生成 | ❌ 缺 |
| Ticket 化 | Task 已是 ticket；有负责人/验收人/验收项 | ✅ 基本有 |
| 上下文喂窄 | Agent prompt 含角色/项目/任务，未含模块卡 | ⚠️ 部分 |
| 独立验收 | 有 reviewer 角色；v0.6.1 增加 Host 独立验证命令 | ✅ 机器验证有；独立验收 AI 缺 |
| 实现者不写测试 | 未强制；Agent 可自己写测试 | ❌ 缺 |
| 失败重试上限 | 没有；失败可无限重派 | ❌ 缺 |
| 契约错误回路 | Decision 董事会可升级，但契约本身不可编辑 | ⚠️ 部分 |
| 集成验收/人玩 | Task 有 playtest 任务，但无固定集成 gate | ❌ 缺 |
| 代码隔离 | v0.6 worktree/branch | ✅ 有 |
| 成本/token | 有 token 预算/计量 | ✅ 有 |
| 不可逆决策 | Decision 董事会 | ✅ 有（未标不可逆） |

## v0.6.1 已补的

- **Host 独立验证**：Task Room 可以输入验证命令，由 Studio Host 在 worktree 里执行；记录 exit code、输出、时间，通过时写 evidence。这样即使 Agent 的 shell 被 Windows ACL 卡住，Verifier 仍能拿到机器证据。
- **Merge Proposal 带 diff/变更文件/验证结果**：提案不再只有摘要，能看到真实改了什么、验证是否通过。
- **测试 25 个通过**，含独立验证命令的真实执行测试。

## 还缺的（建议 v0.7）

按优先级：

1. **PRD/Project Book/INVARIANTS**：项目级 `PRD.md`、`INVARIANTS.md`、`MODULES.md` 路径与只读视图；Agent 每次只加载相关切片。
2. **模块实体 + 契约卡**：Task 增加 `module`、`contractRef`、`kind(new|fix)`、`retryCount`；契约只能由 Architect/Owner 改，实现者改契约 = 新 ticket。
3. **Ticket 类型**：新建型 red→green；改修型先诊断/计划/批准再动代码。
4. **失败上限**：同一 task 连续失败 2 次 → 进入 blocked + 架构师重拆，不允许第三次原地重试。
5. **集成 ticket/playtest gate**：每 N 个任务或每周生成一个集成任务，验收是“打包可玩 + 人玩 10 分钟”。
6. **独立验收角色/模型**：验收会话用不同模型家族，且必须自己跑验证命令；禁止读实现者推理。
7. **文档同步门禁**：任务 done 前检查 PRD/ADR/CONTEXT 是否更新；决策批准后可生成 ADR 草稿。
8. **不可逆标记**：Decision 增加 `reversible`/`scope`，不可逆决策必须 Owner 批准并写 ADR。

## 结论

当前 Studio 的强项是**控制面**（验收门禁、合并治理、董事会、worktree、token 预算）和**代码隔离**；弱项是**知识层**（PRD/模块/契约/不变量/文档同步）和**失败回路**（重试上限、契约回退、集成/人玩 gate）。两段对话给出的流程正好补上这些弱项，不需要推翻现有模型；下一步应把“模块契约卡 + ticket 类型 + 独立验收 + 失败上限 + 集成 gate”做进 Task/Project，而不是再加聊天面板。

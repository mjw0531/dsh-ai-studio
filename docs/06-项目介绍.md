# dsh-ai-studio 项目介绍与开发使用指南

> 适用版本：**v2.5.3**  
> 基准 DSH（DeepSeek Harness，深度求索的 AI 运行时）：**0.2.1-rc.2**  
> 本文面向：想用 AI Agent（智能代理，能调用模型和工具完成任务的运行实例）开发真实项目的人，以及想二次开发这个插件的人。  
> 读法：第一次出现的开发术语会用「中文（English，解释）」标注，完整术语表在[第 15 节](#15-术语注释)。

---

## 1. 这个项目是什么

### 1.1 一句话

**dsh-ai-studio 是 DeepSeek Harness 的一个插件（plugin，挂载到宿主里的扩展模块），把“一个 AI 聊天窗口”变成一间可审计、可验证、可回滚的 AI 工作室。**

它不直接写代码，而是管理“谁在什么范围内、用什么模型、按什么验收标准、经过哪些门禁，把哪个任务做完”。

### 1.2 它解决什么问题

普通 AI 编程通常是：

```text
人提需求 → AI 改代码 → 人自己看 → 可能直接提交
```

问题：

- AI 说“我改好了”，但没有可复现的证据；
- 改坏了主工作区，影响正在开发的功能；
- 没有独立的验证和评审，AI 自己检查自己；
- 多个任务并行时，分支、契约、合并容易冲突；
- 决策没有记录，出了问题不知道谁批准、为什么批准；
- 换电脑后，任务记录和代码分支丢失。

Studio 把这些补成一条闭环：

```text
项目 → 角色 → 任务 → 验收标准 → 隔离执行 → Host 验证
→ 独立评审 → 人工验收 → 人工合并 → 合并后回归
→ 失败升级 / 决策 / 回滚
```

### 1.3 它不是什么

- 不是另一个大模型（LLM，Large Language Model，大语言模型）；
- 不是 IDE（Integrated Development Environment，集成开发环境）；
- 不是自动合并工具：**真实 `git merge`（Git 合并命令，Git 是版本控制系统）只能由人触发**；
- 不替代 DSH，而是 DSH 的 Host（宿主端，Studio 的服务端部分）插件 + Client（客户端，Studio 的页面部分）页面；
- 不能在 Studio 里直接填 GPT/Claude/GLM/Kimi 的 API Key（截至 v2.5.3 仍没有 ProviderProfile UI）；
- Claude Code / Codex 是外部 CLI（Command-Line Interface，命令行工具），需要先在本机登录；
- Cursor 目前只有 IDE 启动器，不是 headless Agent（无界面自动执行代理），暂不支持；
- 独立操作系统（OS，Operating System）窗口 / PWA（Progressive Web App，可安装的网页应用）尚未实现。

## 2. 系统结构

### 2.1 结构图

```text
┌──────────────────────────────────────────────┐
│ DSH（DeepSeek Harness，宿主运行时）           │
│                                              │
│  ┌────────────────────────┐                  │
│  │ Client Plugin（客户端）│                  │
│  │ StudioPage.tsx         │                  │
│  │ 公司 / 决策台 / 知识   │                  │
│  │ 项目 / 任务 / 合并     │                  │
│  │ 团队 / 设置            │                  │
│  └──────────┬─────────────┘                  │
│             │ 同源 HTTP + Bearer Token        │
│  ┌──────────▼─────────────┐                  │
│  │ Host Plugin（宿主端）  │                  │
│  │ /studio-api            │                  │
│  │ 状态机 / 门禁 / 派单   │                  │
│  └──────┬─────────┬───────┘                  │
│         │         │                          │
│         │         └──────────────┐           │
│         ▼                        ▼           │
│  studio.json               项目 Git 仓库      │
│  （治理状态）               ├─ 主工作区       │
│                             ├─ .worktrees/    │
│                             └─ studio/<id>    │
└──────────────────────────────────────────────┘
```

### 2.2 三个关键边界

| 部分 | 作用 | 不应该做什么 |
|---|---|---|
| **Host**（宿主端） | 提供 `/studio-api`、状态机、门禁、派单、验证、合并、存储 | 不把数据接口改成免 token；不自动 push |
| **Client**（客户端） | DSH 页面里的 Studio UI，负责展示和操作 | 不直接读写 `studio.json`；所有操作走 API |
| **项目仓库** | 真实的代码、文档、Git 历史 | Agent 不能直接改主工作区；不能自动 merge/push |

### 2.3 数据放在哪

| 数据 | 位置 | 说明 |
|---|---|---|
| 治理状态 | `%USERPROFILE%\.dsh\studio\studio.json` | 项目、角色、任务、验收、证据、运行、评审、决策 |
| 代码 | 项目仓库 | 由 `repoPath` 绑定 |
| 文档 | 项目仓库 | PRD、INVARIANTS、MODULES、ADR |
| 任务分支 | 项目仓库 | `studio/<taskId>` |
| 隔离工作区 | 项目仓库 `.worktrees/<taskId>` | 每个任务一个，任务结束可保留或清理 |

> `repoPath`（仓库路径）是项目代码仓库在本机的绝对路径。Studio 不把代码复制进 `studio.json`。

## 3. 核心对象

| 对象 | 英文 | 解释 |
|---|---|---|
| 项目 | Project | 一个仓库 + 一套知识文档 + 一组角色 + 一组任务 |
| 角色 | Role | 职责契约（contract，约定的职责边界），不是聊天人设；包含使命、职责、非目标、决策权、模型、执行器、预算 |
| 任务 | Task | 一条可验收的工作，不是一句“帮我改一下” |
| 验收项 | Acceptance | 必须逐条满足的完成条件；全部完成才能 `done` |
| 证据 | Evidence | 可复现的证明，例如测试输出、命令、评审记录、验证记录 |
| 运行 | Run | 一次 Agent 执行记录：prompt、输出、回执、token 消耗 |
| 验证 | Verification | Host 在 worktree 里执行命令，记录退出码和输出 |
| 评审 | Review | 独立验收人 Agent 的只读检查，返回 pass/fail 和 findings |
| 决策 | Decision | Owner 级别的项目决策，必须留结论和理由 |
| 合并提案 | Merge Proposal | 任务完成后提交的合并申请：摘要、风险、回滚、分支、base |
| 模块 | Module | 代码模块的契约：职责、接口摘要、允许/禁止路径、依赖 |
| 分支 | Branch | Git 分支；Studio 为每个任务创建 `studio/<taskId>` |
| 工作树 | Worktree | Git 工作树；同一个仓库的独立检出目录，用来隔离任务 |

### 3.1 任务状态

```text
backlog（待规划）
  ↓
ready（可开始）
  ↓
running（执行中）
  ├── blocked（阻塞）
  └── review（待验收）
        ├── running（打回修改）
        └── done（完成，锁定）
```

允许的状态流转：

| 当前 | 可以到 |
|---|---|
| `backlog` | `ready` |
| `ready` | `backlog`、`running` |
| `running` | `ready`、`blocked`、`review` |
| `blocked` | `ready`、`running` |
| `review` | `running`、`blocked`、`done` |
| `done` | 无（完成即锁定） |

> 状态机（state machine，规定“什么状态只能到什么状态”的规则）由 Host 强制执行，UI 不能随便跳。

## 4. 工作流总览

### 4.1 一张图

```text
1. 建项目
   ↓
2. 绑定 Git 仓库
   ↓
3. 绑定 PRD / INVARIANTS / MODULES（可选但推荐）
   ↓
4. 配置角色：Lead / Architect / Builder / Verifier
   ↓
5. 建任务：目标 + 验收项 + 验证命令 + 模块
   ↓
6. 派单
   ├─ 创建 .worktrees/<taskId>
   ├─ 创建 studio/<taskId> 分支
   ├─ Agent 在 worktree 内实现
   ├─ Host 自动 git add + commit
   └─ 回执必须含 summary + evidence
   ↓
7. Host 验证
   └─ 在 worktree 跑验证命令，记录退出码/输出
   ↓
8. 独立评审
   └─ 验收人角色只读检查 diff / 验证输出 / 验收标准 / 契约
   ↓
9. 人工验收
   ├─ 勾完所有验收项
   ├─ 补至少一条 evidence
   └─ review → done
   ↓
10. 合并提案
    └─ review → approved → merged
   ↓
11. 人工执行 git merge --no-ff
   ↓
12. 合并后回归
    ├─ pass：记录 post-merge verification
    └─ fail：生成决策，建议回滚
   ↓
13. 人工回滚（仅回归失败时）
    └─ git revert -m 1 <mergeCommit>
```

### 4.2 每一步谁负责

| 步骤 | Owner（老板/人） | Agent | Host（宿主） |
|---|---|---|---|
| 建项目、绑仓库 | ✅ | ❌ | 保存 |
| 写 PRD/契约 | ✅ | 可建议 | 只读展示 |
| 建任务、写验收 | ✅ | 可建议 | 校验字段 |
| 派单 | 触发 | 执行 | 创建 worktree、提交、记录 |
| 验证 | 可触发 | ❌ | 执行命令、记录 |
| 评审 | 可触发 | 验收人 Agent | 新开只读会话、记录 |
| 完成 | ✅ 勾验收 | ❌ | 门禁检查 |
| 合并批准 | ✅ | ❌ | 记录 |
| 真实 merge | ✅ 人触发 | ❌ | 检查并执行 |
| 回滚 | ✅ 人触发 | ❌ | 执行 revert |
| 决策 | ✅ Owner | 只能建议 | 保存结论 |

> **Owner** 是项目所有者，通常是你。Agent 不能替 Owner 做项目级决策。

## 5. 第一次配置：开发前准备

### 5.1 安装与打开

**方式 A：本地目录**

DSH → Plugins → Add plugin → 本地目录：

```text
D:\dsh-ai-studio
```

或使用 tarball（打包好的压缩安装包）：

```text
D:\dsh-ai-studio\packages\dsh-studio\dsh-ai-studio-2.5.3.tgz
```

**方式 B：GitHub 根目录**

```text
https://github.com/mjw0531/dsh-ai-studio
```

仓库根目录的 `package.json` 已包含 `dsh.bundle` 和 `dsh.client` 清单。

安装后完全退出 DSH（含托盘），重新打开，左侧应出现 **AI 工作室**。

### 5.2 建项目并绑定仓库

设置 → 代码仓库：

- 项目名；
- 项目描述；
- **仓库绝对路径**，例如 `D:\projects\my-game`；
- 可选：总 token 预算。

绑定前确认：

```powershell
cd D:\projects\my-game
git status
git config user.name
git config user.email
```

仓库必须是 **Git 仓库**（有 `.git` 目录），并且配了提交身份。  
否则 merge 时会报 `Committer identity unknown`。

### 5.3 写项目知识

知识页可以绑定三个文件：

| 文件 | 作用 |
|---|---|
| **PRD**（Product Requirements Document，产品需求文档） | 做什么、给谁用、验收边界 |
| **INVARIANTS**（不变量，任何时候都不能破坏的规则） | 例如“存档不能丢”“服务端权威” |
| **MODULES**（模块契约清单） | 每个模块的职责、接口、允许修改的路径 |

绑定后，任务 `done` 前必须勾选 **文档已同步**（`docsSynced=true`），否则完成门禁不通过。

### 5.4 配置角色

建议至少四个角色：

| 角色 | 职责 | 建议模型/执行器 |
|---|---|---|
| **Lead** | 拆任务、排优先级、写验收 | DSH Agent |
| **Architect** | 架构、模块边界、契约、重拆 | Claude Code 或强模型 |
| **Builder** | 在 worktree 里写代码 | Codex CLI 或 DSH Agent |
| **Verifier** | 只读评审、找问题 | 与 Builder 不同的模型 |

角色字段：

- `mission`（使命）：这个角色为什么存在；
- `responsibilities`（职责）：负责什么；
- `nonGoals`（非目标）：明确不负责什么，防止越界；
- `decisionRights`（决策权）：能决定什么；
- `model`（模型 ID）：留空表示继承 DSH 部署默认模型；
- `executor`（执行器）：`DSH Agent`、`Claude Code`、`Codex CLI`；
- `tokenBudget`（单次运行 token 预算）；
- `dailyTokenBudget`（每日 token 预算）。

> **Token** 是模型处理文本的计量单位，可理解为“字数/词块”。预算用来防止一次任务烧掉过多调用量。

### 5.5 配置模块契约

模块页填写：

- 模块名；
- 职责；
- 契约文件路径，例如 `docs/modules/auth.md`；
- 契约文本摘要；
- `allowedPaths`（允许改的路径），例如 `src/auth/`、`test/auth/`；
- `forbiddenPaths`（禁止改的路径）；
- `dependsOn`（依赖模块）。

派单时模块契约会进入 Agent 上下文。  
如果 Agent 改了契约文件、禁止路径，或越出允许的 `src/`、`test/` 路径，任务会：

```text
blocked（阻塞） + 生成「契约越界」决策
```

### 5.6 准备验证命令

每个任务要有一条 **Host 可执行的验证命令**，例如：

```powershell
npm test
```

或：

```powershell
pnpm typecheck
pnpm test
```

要求：

- 非交互式（不能等人输入）；
- 退出码能表达成功/失败；
- 在 worktree 内可运行；
- 输出能作为 evidence（证据）。

> **退出码**（exit code）是命令结束时返回的数字，`0` 通常表示成功，非 `0` 表示失败。Host 用它判断验证是否通过。

## 6. 日常开发闭环

### 6.1 建任务

任务页 → 新建任务，填：

| 字段 | 说明 | 示例 |
|---|---|---|
| 标题 | 一句话说明 | 增加登录接口 |
| 目标 | 为什么要做、做成什么样 | 支持邮箱密码登录，失败返回 401 |
| 负责人 | 谁执行 | Builder |
| 验收人 | 谁独立评审 | Verifier |
| 优先级 | P0/P1/P2 | P1 |
| 验收标准 | 一行一条，可观察 | 登录成功返回 token；密码错误返回 401 |
| 验证命令 | Host 执行 | `npm test` |
| 模块 | 影响哪个模块 | `auth` |
| 契约引用 | 相关契约路径 | `docs/modules/auth.md` |
| 票类型 | 新建型 / 改修型 | 新建型 |
| 诊断 | 仅改修型必填 | 登录失败时错误码被吞掉 |
| 修改计划 | 仅改修型必填 | 在 controller 捕获并映射 401 |

#### 新建型与改修型

- **新建型（`new`）**：新功能。建议按 **red → green** 做：
  1. **red**：先写一个会失败的测试；
  2. **green**：再写最小实现让测试通过；
  3. 重构。
- **改修型（`fix`）**：修 bug。必须先写 **诊断（diagnosis）** 和 **修改计划（plan）**，否则不能派单。

> **TDD**（Test-Driven Development，测试驱动开发）就是先写失败测试，再写实现。  
> **red→green** 是 TDD 的最小循环：红（测试失败）→ 绿（测试通过）。

### 6.2 派单

任务详情 → 派单。

Host 会：

1. 检查任务状态是 `backlog` 或 `ready`；
2. 检查有负责人；
3. 创建 worktree：

```text
<repo>/.worktrees/<taskId>
```

4. 创建分支：

```text
studio/<taskId>
```

5. 调用角色配置的执行器；
6. 等待 Agent 返回结构化回执；
7. 成功后把 worktree 里的改动（含未跟踪文件）自动 `git add` + `git commit`；
8. 任务进入 `review`。

回执必须包含：

```json
{
  "summary": "非空摘要",
  "evidence": ["至少一条证据"]
}
```

缺 `summary` 或 `evidence`：

```text
Run failed → 任务退回 ready
```

> **回执**（receipt）是 Agent 交工时返回的结构化结果，不是随便一段聊天。  
> **未跟踪文件**（untracked files）是 Git 还没纳入版本控制的新文件；Host 会一并提交，避免漏文件。

### 6.3 Host 验证

任务详情 → 验证。

Host 在 **worktree** 内执行任务验证命令，记录：

- `command`（命令）；
- `exitCode`（退出码）；
- `output`（输出）；
- `passed`（是否通过）。

验证通过只写 **evidence**，不会自动勾验收，也不会自动 `done`。

> **Worktree** 是 Git 的“同一仓库、多个工作目录”能力。任务在独立目录里改，主工作区不受影响。  
> **Evidence** 是可复现证据，不是“我觉得没问题”。

### 6.4 独立评审

任务详情 → 独立评审。

验收人角色会新开一个**只读** Agent 会话，检查：

- `diff`（代码差异）；
- Host 验证输出；
- 验收标准；
- 契约边界。

返回：

```text
pass / fail + findings（发现的问题）
```

代码任务没有 `pass` 不能 `done`。

如果评审模型和实现模型相同，界面会提示“同族评审”，提醒共享盲点。

> **Diff** 是两次提交/两个版本之间的代码差异。  
> **只读评审** 意味着评审 Agent 不能改代码，只能看和判断。

### 6.5 人工验收与完成

人勾完所有验收项，补至少一条 evidence；如果项目绑了知识文档，勾“文档已同步”；然后：

```text
review → done
```

`done` 是完成态，不能再流转。

> **验收项**（Acceptance）是“完成的定义”，必须可观察、可验证。  
> **完成门禁** 是进入 `done` 前必须满足的规则集合。

### 6.6 合并提案与人工合并

`done` 后创建合并提案，填写：

- 摘要；
- 风险等级；
- 回滚方式；
- base 分支；
- 评审备注。

状态：

```text
review → approved → merged
        ↘ rejected
```

执行真实合并前，Host 检查：

- 提案是 `approved`；
- 当前在 base 分支；
- 工作区干净；
- 任务分支存在；
- 仓库配了 `user.name/email`。

然后由**人**触发：

```bash
git merge --no-ff studio/<taskId>
```

冲突自动 `abort`，不自动 push。

> **base** 是合并目标分支，通常是 `main` 或 `develop`。  
> **`--no-ff`** 表示即使能快进也保留一个 merge commit，便于审计。  
> **abort** 是取消这次合并，回到合并前状态。

### 6.7 合并后回归

merge 成功后，Host 在项目仓库执行任务验证命令：

- 通过：记录 post-merge verification；
- 失败：自动生成“合并后回归失败”决策，附 merge commit 和回滚建议；不会自动回滚。

> **回归**（regression）是“改完新功能后，原有功能有没有被弄坏”的验证。

### 6.8 人工回滚

只有满足以下条件才能回滚：

- 提案是 `merged`；
- post-merge 回归失败。

命令由 Host 执行：

```bash
git revert -m 1 --no-edit <mergeCommit>
```

记录 rollback commit；不 `reset`，不 `push`。

> **revert** 是生成一个“反向提交”来撤销某次提交，保留历史。  
> **reset** 是移动分支指针/丢弃提交，风险更高；Studio 不使用 reset 回滚。  
> **`-m 1`** 表示对 merge commit 保留第一父提交（通常是 base 主线）。

## 7. 怎么写好任务

### 7.1 好任务的标准

一条任务应该：

1. **只做一件事**：能在一个 worktree 内完成；
2. **验收可观察**：不是“代码优雅”，而是“接口返回 401”；
3. **验证可执行**：有明确命令和退出码；
4. **范围可控**：绑定模块和允许路径；
5. **证据可复现**：别人按命令能跑出同样结果。

### 7.2 验收标准示例

差的验收：

```text
- 登录功能做好
- 代码质量高
```

好的验收：

```text
- 正确邮箱密码返回 200，响应含 token
- 错误密码返回 401，响应不含 token
- 连续 5 次失败后返回 429
- npm test 退出码为 0
```

### 7.3 验证命令示例

```powershell
npm test
```

```powershell
pnpm typecheck
pnpm test
```

```powershell
pytest -q
```

不要用：

```text
打开浏览器手动点一下
```

因为 Host 不能交互。

### 7.4 改修型任务模板

```text
标题：修复登录失败时错误码被吞掉

诊断：
- 复现：错误密码时接口返回 200
- 根因：controller 捕获异常后没有映射 401
- 影响：客户端无法提示密码错误

修改计划：
- 在 auth controller 捕获 AuthError
- 映射为 HTTP 401
- 增加失败登录测试

验收：
- 错误密码返回 401
- 正确密码仍返回 200
- npm test 通过
```

### 7.5 任务拆分建议

- 一个任务对应一个可合并的改动；
- 大功能拆成“接口 → 实现 → 集成 → playtest”；
- 每完成 3 个任务，Studio 会自动生成一张集成/playtest backlog ticket；
- 连续失败 2 次，任务 blocked，并自动生成 Architect 重拆 ticket。

## 8. 一个完整例子：给项目加“用户登录”

### 8.1 准备

1. 项目绑定仓库 `D:\projects\demo`；
2. 知识页绑定 `docs/PRD.md`、`docs/INVARIANTS.md`、`docs/MODULES.md`；
3. 配置角色 Lead、Architect、Builder、Verifier；
4. 配置模块 `auth`：
   - 允许路径：`src/auth/`、`test/auth/`；
   - 禁止路径：`src/payments/`；
   - 契约：`docs/modules/auth.md`。

### 8.2 建任务

```text
标题：增加邮箱密码登录接口

目标：客户端可以用邮箱和密码登录，成功后拿到会话 token。

负责人：Builder
验收人：Verifier

验收：
- POST /login 正确凭据返回 200 和 token
- 错误密码返回 401
- 连续 5 次失败返回 429
- 不影响已有注册接口

验证命令：npm test
模块：auth
契约：docs/modules/auth.md
类型：新建型
```

### 8.3 派单

Host：

```text
创建 D:\projects\demo\.worktrees\task-xxx
创建分支 studio/task-xxx
```

Builder Agent 在 worktree 内写代码和测试。

### 8.4 验证

Host 在 worktree 内：

```powershell
npm test
```

输出和退出码写入 evidence。

### 8.5 评审

Verifier 只读检查：

- 登录 diff；
- 401/429 测试；
- 是否改了 `src/payments/`；
- 是否破坏注册接口。

返回 `pass` 或 `fail`。

### 8.6 完成与合并

人：

1. 勾完验收；
2. 补证据；
3. 勾“文档已同步”；
4. `review → done`；
5. 创建合并提案；
6. 批准；
7. 人触发 merge。

### 8.7 回归

merge 后 Host 再跑 `npm test`：

- 通过：记录；
- 失败：生成决策，人工决定回滚或修复。

## 9. 角色、模型与执行器

### 9.1 角色分离

最低建议：

```text
Lead（拆任务） → Builder（实现） → Verifier（评审） → Owner（验收/合并）
```

Architect 负责跨模块设计、契约、重拆。

不要让同一个角色既实现又评审；如果模型相同，界面会提示“同族评审”。

### 9.2 模型选择

角色的 `model` 是**模型 ID**（model identifier，供应商标识某个模型的字符串）。  
留空表示继承 DSH 部署默认模型。

> **Provider**（模型供应商/服务提供方）是实际提供模型 API 的服务，例如 DeepSeek、OpenAI、Anthropic。  
> **API**（Application Programming Interface，应用程序接口）是程序之间调用能力的约定。  
> **API Key** 是调用 API 的密钥；Studio 不把它写进 `studio.json`。

当前 v2.5.3：

- DSH Agent 使用 DSH 已配置的 Provider 和模型；
- Claude Code / Codex 使用本机 CLI 登录态；
- 没有 Studio 侧 GPT/Claude/GLM/Kimi API Key 配置 UI；
- 外部 CLI 需要先登录，且仍走同一套门禁。

### 9.3 执行器

| 执行器 | 说明 | 前提 |
|---|---|---|
| **DSH Agent** | DSH 内部 Agent 运行时 | DSH 已配置模型 |
| **Claude Code** | Anthropic 的 CLI 编程代理 | 本机 `claude` 已登录 |
| **Codex CLI** | OpenAI 的 CLI 编程代理 | 本机 `codex` 已登录 |

外部执行器只在 worktree 内、headless（无界面自动执行）运行，仍然必须：

1. 输出 `summary + evidence`；
2. 通过 Host 验证；
3. 通过独立评审；
4. 由人 merge。

### 9.4 Token 预算

- `tokenBudget`：单次运行上限；
- `dailyTokenBudget`：每日上限；
- 项目 `tokenBudget`：项目总预算。

> **Context**（上下文）是模型一次能看到的文本范围；超出会被截断或压缩。  
> **Token** 是计费/限制单位，不等于汉字数，但可粗略理解为文本量。

## 10. 门禁清单

> **门禁**（gate）是“不满足条件就不能进入下一步”的强制检查。

| 门禁 | 条件 | 不满足时 |
|---|---|---|
| 完成门禁 | 所有验收 `done` + 至少 1 条 evidence | 不能 `done` |
| 文档门禁 | 绑定知识文档时 `docsSynced=true` | 不能 `done` |
| 验证门禁 | 代码项目有通过的 Host verification | 不能提交合并提案 |
| 评审门禁 | 代码任务有独立评审 `pass` | 不能 `done` |
| 合并门禁 | 提案 `approved`、在 base、工作区干净、分支存在、Git 身份存在 | 拒绝 merge |
| 契约门禁 | 不改契约文件/禁止路径/越界 | `blocked` + 决策 |
| 失败门禁 | 连续失败 2 次 | `blocked` + 决策 + 重拆 ticket |
| 不可逆门禁 | `reversible=false` 的决策必须写结论和理由 | 拒绝批准 |
| ADR 门禁 | 只有人确认才写 `docs/adr/` | 不自动写 |
| 回滚门禁 | 只有 merged + 回归失败 | 拒绝回滚 |
| 集成门禁 | 每完成 3 个任务 | 自动生成 backlog 集成/playtest ticket |
| 外部执行器门禁 | CLI 已登录、worktree 内 headless、回执完整 | Run failed |

## 11. 失败、阻塞、决策

### 11.1 连续失败

同一任务连续失败 2 次：

```text
blocked（阻塞）
+ 生成决策
+ 生成 Architect 重拆 ticket（backlog）
```

不允许第三次原地重试。

### 11.2 契约越界

代码 Run 如果：

- 改了模块契约文件；
- 改了禁止路径；
- 越出允许的 `src/`、`test/` 路径；

则：

```text
blocked + 「契约越界」决策
```

### 11.3 决策台

决策台（Decision Desk）处理：

- Agent 提出的项目级决策；
- 人手动提出的决策；
- 跨支线契约冲突；
- 连续失败升级；
- 合并后回归失败。

Owner 批准/拒绝，必须写结论和理由。

不可逆决策（`reversible=false`）批准后：

1. 自动生成 Markdown ADR 草稿；
2. 保存在决策记录里；
3. 人工确认后才写入 `docs/adr/`。

> **ADR**（Architecture Decision Record，架构决策记录）是记录“为什么这样设计”的短文档，通常包含背景、决策、替代方案、后果。

## 12. 数据、备份与迁移

### 12.1 导出/导入 JSON

页面「导出」下载完整 `studio.json`；「导入」恢复。

导入时 Host：

1. 备份当前文件为 `studio.json.pre-import-*`；
2. 校验 schema 和结构；
3. 拒绝更高 schema；
4. 成功后才替换。

> **Schema** 是数据结构的版本化定义；`schemaVersion` 变化表示字段可能不兼容。  
> **Migration**（迁移）是把旧结构升级到新结构的代码。

### 12.2 项目包

设置 → 代码仓库 → 导出项目包，生成 `tar.gz`：

| 文件 | 作用 |
|---|---|
| `studio.json` | 治理状态 |
| `project.bundle` | `git bundle --all`，含所有分支 |
| `manifest.json` | 项目、schema、版本、SHA-256 |
| `README.txt` | 迁移说明 |

导入：

1. 输入项目包绝对路径 + 目标空目录；
2. 校验 manifest 和 SHA-256；
3. 解压；
4. `git clone project.bundle <target>`；
5. 备份并导入 `studio.json`；
6. 重绑 `repoPath`。

不包含：

- API Key；
- `.worktrees`；
- 未提交文件。

> **Bundle** 是 Git 的“单文件仓库包”，可以把所有分支/提交装进一个文件。  
> **SHA-256** 是文件指纹，用来校验文件是否损坏/被改。  
> **Manifest** 是包内清单，说明包里有什么、版本、校验和。

### 12.3 换设备

1. 新机安装 DSH + 插件；
2. 复制项目包；
3. 导入；
4. 重新登录 Claude Code/Codex（如果使用）；
5. 活跃任务第一次派单时，从 `origin/studio/<taskId>` 重建 worktree。

## 16. 常见问题

### Q1：Agent 说改好了，但测试没跑

让 Host 跑验证：

```text
任务详情 → 验证
```

Agent 的“我改好了”不是证据，Host 的退出码和输出才是。

### Q2：merge 报 `Committer identity unknown`

给项目仓库配置身份：

```powershell
cd D:\projects\your-project
git config user.name "Your Name"
git config user.email "you@example.com"
```

### Q3：导入报 schema 不支持

导入文件比当前插件新。先升级 DSH/Studio，再导入。

### Q4：侧栏没有「AI 工作室」

1. 确认插件已安装；
2. 完全退出 DSH（含托盘）；
3. 重启；
4. 检查 `cordis.patch.yml` 的包名是否与 `package.json` 的 `name` 一致；
5. 用 `studio-test` profile 做隔离烟测。

### Q5：外部执行器报未登录

```powershell
claude
codex login
```

### Q6：Windows 上 Agent 能改文件但不能跑测试

可能是 Windows ACL（Access Control List，访问控制列表）限制。  
用 Host 验证，Host 会在 worktree 内执行并如实记录 blocker，不能伪造通过。

### Q7：为什么不能自动 merge？

因为真实 `git merge` 是高风险操作，Studio 设计为**人触发**：

- 需要 approved 提案；
- 当前在 base；
- 工作区干净；
- 分支存在；
- Git 身份存在；
- 冲突 abort；
- 不自动 push。

### Q8：项目包包含 API Key 吗？

不包含。项目包只含状态、Git bundle、manifest、说明；密钥和 CLI 登录态不在里面。

## 18. 当前限制（务必知道）

- 只在 DSH `0.2.1-rc.2` 上验证；更高版本是尽力兼容；
- 没有 Studio 侧 GPT/Claude/GLM/Kimi API Key 配置；
- Claude Code / Codex 需要本机登录；
- Cursor 没有 headless Agent，暂不支持；
- 没有独立 OS 窗口/PWA；
- 合并必须由人触发，不自动 push；
- 回滚必须由人触发，不自动回滚；
- 项目包导入需要手动输入绝对路径；
- 自动集成/playtest ticket 只生成 backlog，不自动派单；
- npm 发布受 npm 自身 staged publishing/审核流程影响，不作为安装前提。

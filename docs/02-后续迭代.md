# 后续迭代计划

基于 v0.5.1 的现状、用户与 DeepSeek 的对话补充，以及 Studio 的核心原则制定。顺序不是功能堆叠，而是**每一版都让上一版的假设接受真实项目检验**。

## 迭代原则

1. **先控制面，后执行面**：项目/任务/验收/合并治理已经是事实来源；Agent 执行必须写入这套事实，而不是另起一套聊天记录。
2. **每一次执行都产生可合并结果包**：`artifacts / decisions / contract_deltas / rejected_options`。
3. **决策升级必须显式**：支线局部决策什么时候变成项目级约束，要有门禁，不能靠 Agent 口头约定。
4. **可见性是权限**：验收者/主线不应加载实现支线的完整推理；Scope 隔离优先于 UI 隐藏。
5. **不编造经济数据**：token/成本必须来自真实执行计量；没有数据就显示“待接入”。
6. **前五分钟决定产品**：安装后要有模板、默认角色、示例任务；不能给用户一个空工作台。

## 来自 Edge / DeepSeek 免费对话的补充

用户提示可以使用 Edge 里的 DeepSeek 免费对话页做功能评审。本轮已读取页面内容，其中四条建议成立：

1. **第一屏是公司仪表盘**：总预算、已消耗、成本占比、待裁决冲突、被否决方案。——v0.3 已实现前四类中的控制面部分。
2. **角色配置要有“薪资”**：架构师用贵模型、实现者用便宜模型；Preset 选模型和 token 预算。——纳入 v0.4。
3. **汇入裁决要有“董事会”视图**：冲突描述、双方支线初始目标、成本、架构师建议、Owner 决定。——纳入 v0.5。
4. **组织架构可调整**：动态增减支线类型、调整角色权限。——纳入 v0.5.1 的 Scope/Preset 配置。

一句话总结：产品不是“更聪明的聊天框”，而是**一个人以管理者方式运营 AI 组织的操作系统**。UI 的信息架构应是：仪表盘 → 支线看板 → 裁决队列 → 决策库。

## v0.4 · Agent 派单与结构化回执（已完成）

**目标**：Task Room 真正能启动一个 DSH 子会话，并把结果写回任务，而不是只记录人为状态。

**v0.4.0 实际落地**：`agents.create` + `agentPresets.mount` 启动 DSH Agent；模型路由优先使用已认证的 `deepseek-account`；Agent 以只读分析模式返回结构化回执；`completeRun` 把回执写回证据，缺 `summary`/`evidence` 时任务退回 `ready` 而不是进入 `review`；Run 记录 token 消耗。代码执行/worktree 留到 v0.6。

范围：

- Role Card → DSH Agent Preset 编译（persona + 工具 + 技能 + 模型策略）。
- Role “薪资”配置：模型档位/模型政策、单任务 token 预算、每日上限；UI 显示为岗位配置，而不是隐藏参数。
- Project 预算：总 token/费用上限、按角色/任务分配；Owner Dashboard 显示预算与真实消耗。
- `dispatch_task`：为 Task 创建子会话/子代理，注入角色卡、任务目标、验收标准、项目约束和预算。
- 结果包 schema：
  ```json
  {
    "summary": "一句话结论",
    "evidence": ["可复现的证据"],
    "artifacts": [{ "kind": "diff|test|doc|replay", "path": "..." }],
    "decisions": [{ "title": "...", "rationale": "...", "scope": "branch|project" }],
    "contractDeltas": [{ "contract": "...", "change": "..." }],
    "rejectedOptions": [{ "option": "...", "reason": "..." }],
    "blockers": ["阻塞"]
  }
  ```
- `receipt` 回执进入 Task，Agent 不能自己把任务推到 `done`；只能提交到 `review`。
- 成本台账：从 DSH session/token meter 读取每个 Run 的 token/成本，写入 `Run` 记录。
- Owner Dashboard 增加真实“Agent 运行中/失败/成本”数据。

验收：

- ✅ 一条真实任务由 DSH Agent 完成并回执（隔离 profile，71,629 tokens）；
- ✅ 回执缺字段时无法进入 review（任务退回 ready，Run 标记 failed）；
- ✅ 重启后 Run/token 持久化可追溯；
- ⏳ 运行中预算硬停（v0.4.1；当前是派单前预检 + 完成后超限告警）。

不做：自动合并、跨机器调度、嵌套团队。

v0.4.1 待补：运行中 token 硬停、`normalizeReceipt` 单测、Agent session 与 Run 的可视化关联、真实金额报价。

## v0.5 · 决策董事会 + 支线/契约（v0.5.1 已完成）

**目标**：把“支线”从任务字段升级为可审计对象，并把决策升级做实。

**v0.5.0 实际落地**：`Decision` 持久化（pending/approved/rejected）、独立董事会页面、Agent 项目级决策自动进入待裁决、Owner 批准/拒绝并记录结论与理由、公司仪表盘“需要你”入口。

**v0.5.1 实际落地**：`Branch` 持久化与项目支线面板、派单自动登记支线、Agent `contractDeltas` 写入 `contractChanges`、两条支线改同一契约且内容不同时自动升级为待裁决 Decision（带双方变更选项）。Scope 强隔离、Project Book 仍待后续。

范围：

- `Branch` 对象：状态、可见文件集、绑定角色、汇入契约、结果包。
- `Decision` 对象：局部决策 vs 项目级约束；升级门禁：
  - 影响多模块/契约/不可逆 → 必须升级；
  - 由 Architect/负责人裁决，写入 ADR/Decision；
  - 后续支线可见。
- Scope 隔离：
  - 实现支线只加载任务切片 + 契约 + 约束；
  - 验收支线只加载验收标准 + 产物；
  - 主线只加载约束 + 汇入摘要 + 决策。
- Project Book：从 Canon 生成索引，按触发词/范围注入；带来源/owner/freshness。
- Owner Dashboard 增加“决策升级待裁决”入口。
- “董事会”视图：契约冲突描述、双方支线初始目标、成本消耗、架构师建议、Owner 最终决定；决定写入 Decision/ADR。
- 组织可调整：动态增减支线类型、角色/Scope preset、权限边界。

验收：

- ✅ 决策进入董事会，Owner 能批准/拒绝并记录结论与理由；
- ✅ Agent 的项目级决策自动进入待裁决；
- ✅ 决策持久化、重启可追溯、公司仪表盘有“需要你”入口；
- ✅ 两个支线并行改同一契约，系统自动生成待裁决决策；
- ✅ 董事会卡片展示双方契约变更选项与 token 成本；
- ✅ 支线、契约变更持久化，`branch` 面板可见；
- ⏳ Scope 强隔离，验收者上下文不出现实现者推理；
- ⏳ 决策自动生成 ADR 草稿并关联契约。

v0.5.2/v0.6 待补：Scope 强隔离、Project Book、决策→ADR 草稿、代码执行/worktree。

不做：向量数据库、自动摘要替代 Canon、无限嵌套 Scope。

## v0.6 · Git worktree 与代码执行（v0.6.1 已完成代码编辑 + 独立验证）

**目标**：从“记录合并”走向“安全执行合并”，但不牺牲可控性。

**v0.6.0 实际落地**：Project 绑定 `repoPath`；每个 Task 自动创建 `.worktrees/<taskId>` 与 `studio/<taskId>` 分支；Agent 在 worktree 内以代码模式编辑文件，Run 记录 `branchName / workspacePath / diffStat`；主工作区不被直接修改。已在 `D:\AIgame` 上真实派单，Agent 修改 README 并产生 `1 file changed, 10 insertions(+)` 的 diff。Windows 沙箱 ACL 可能阻止 Agent 启动 shell 跑测试，Run 会如实记录 blocker。

**v0.6.1 实际落地**：Task 增加 `verifyCommand`；Host 独立验证在 worktree 内执行命令，记录 exit code/输出并写 evidence；Merge Proposal 记录 `diffStat / changedFiles / verificationId`。真实验证 `npm test` 通过 3/3，解决了 Agent shell ACL 阻断时无法拿机器证据的问题。

范围：

- ✅ Project 绑定 repoPath；每个 Task 一个 worktree/branch。
- ✅ Agent 在 worktree 内编辑代码，Run 记录 diff。
- ⏳ 干净工作区检查、基础分支检查、冲突预检。
- ⏳ Merge Proposal 增加真实 diff、contract_deltas、rollback commit、review evidence。
- ⏳ 合并队列串行化；合并后跑回归；失败自动回滚。
- ⏳ 高风险/二进制资产（Unity scene/prefab、LFS）走独占租约，不做自动合并。
- ⏳ 人类/Integrator 明确批准后才执行 `git merge`。

验收：

- ✅ Agent 能在独立 worktree 中修改代码并返回 diff；
- ⏳ 两个并行 Task 安全合并；
- ⏳ 制造一次冲突，系统阻断并生成决策请求；
- ⏳ 回滚可执行；
- ⏳ 任何自动操作都有审计事件；
- ⏳ Windows 沙箱 ACL 下的测试执行修复。

不做：自动解决语义冲突、自动合并二进制资产、无审批合并主干。

## v1.1 · 独立评审（v1.1.0 已完成）

**目标**：代码任务能不能 done，不再由实现者自己说了算。

**v1.1.0 实际落地**：
- Task Room 增加「独立评审」：由验收人角色另开 Agent 会话，只看 diff、Host 验证输出和验收标准，不改代码。
- 评审返回 `pass|fail`、summary、findings，记录模型和 token。
- 代码任务（有 worktree Run）done 前必须有通过的独立评审；否则 `review_required`。
- 实战：对 `task-0bb68f12` 跑了一次真实评审，`deepseek-flash` 返回 pass，23,489 tokens，并指出“测试未覆盖 replay:verify CLI”这个非阻塞风险。

验收：✅ 评审门禁测试；✅ 真实评审运行；✅ Web 端显示评审结果；31 个单测通过。

## v1.4 · 人工触发 Git merge（v1.4.0 已完成）

**目标**：从“记录合并”走到“人批准后真正 merge”，但不引入自动合并。

**v1.4.0 实际落地**：
- 已批准的 Merge Proposal 可在 Task Room 执行 `git merge --no-ff`。
- 前置检查：当前分支必须是 proposal.base、工作区必须干净、任务分支必须存在、不能有未完成 merge。
- 冲突时自动 `git merge --abort`，不改主工作区；成功后记录真实 merge commit。
- 不自动 push，不自动切分支，不自动合并。
- 保留“仅记录合并”作为无 Git 环境/人工外部合并的 fallback。

验收：✅ 真实临时仓库 merge 测试；✅ 35 个单测通过。

## v1.6 · 合并后回归（v1.6.0 已完成）

**目标**：merge 成功不等于集成通过；合并后必须再跑一次验证。

**v1.6.0 实际落地**：

## v1.7 · 合并失败升级（v1.7.0 已完成）

**目标**：合并后回归失败不能只留在 Task Room 的红色提示里。

**v1.7.0 实际落地**：
- post-merge Verification 失败时自动生成「合并后回归失败」决策。
- 决策带 merge commit、命令、exit code、输出摘要，以及两个选项：回滚 / 保留并修复。
- 附回滚建议 `git revert <commit>` 或 `git reset --hard <commit>^`。
- 同一任务只生成一次，避免重复决策。
- 不自动回滚，不自动 push。

验收：✅ 36 个单测通过；✅ 失败决策去重测试。
